# H576 Dense / 2:4 Sparse 数据格式约定 v0.1

日期：2026-10-22。格式标识：`H576_SPARSE24_SPLIT128_V1`。

**用途：作为下一版 Python 打包器、HLS 计算核、testbench 和 runtime 共同遵守的开发约定。当前只新增本文档，尚未实现打包器或 Sparse IP，也未完成该物理格式的仿真验收。旧 H576 IP、runtime 和候选包不自动支持本格式。**

一句话概括：**保留 128 bit AXI 总线；Dense 传完整 INT8 权重；Sparse 分别传两个 INT8 权重值和两个压缩的位置索引，不再重复传完整 mask。**

## 1. 计算内容与职责

计算核只负责整数矩阵乘法：

```text
Xq[M,K] × Wq[K,N] → Y_int32[M,N]
```

- X、W 按有符号 INT8 二进制补码解释；Y 是有符号 INT32。
- 乘法必须先按有符号数计算，再扩展并累加；不能把负数当 UINT8。
- 每次调用从零开始累加，不读取旧 Y，不做跨调用累加。
- 量化、剪枝、bias、scale、反量化及模型后处理在软件侧，维持现有数值规则，不在本次核中增加。
- 当前候选的权重量化范围是 `[-127,127]`；数据解码和边界测试仍须正确处理 INT8 的 `-128`。
- INT64 软件参考检查结果可表示为 INT32后再转换；合法调用不得发生 INT32 溢出，不允许静默截断或改成饱和运算。Host 按核的尺寸白名单检查，并以 `K × 16384 <= 2147483647` 作保守最坏界检查。

Dense / Sparse 是每次调用的参数，不把模型层号写死进电路。

## 2. 共用布局与控制信息

所有矩阵采用行优先、紧密排列；**不为每一行、每一列或每个 tile 单独插入 padding**。

| 数据 | 逻辑索引 | 线性元素索引 |
|---|---|---|
| X | `Xq[m,k]` | `m*K+k` |
| Dense W | `Wq[k,n]` | `k*N+n` |
| Y | `Y_int32[m,n]` | `m*N+n` |

调用至少提供 `M、K、N、mode、X_addr、W_data_addr、W_meta_addr、Y_addr`。

| mode | 含义 | W_data | W_meta |
|---:|---|---|---|
| 0 | Dense | 完整 `Wq[K,N]` | 不读取 |
| 1 | Sparse24 | `values[K/4,N,2]` | 打包后的 `positions[K/4,N,2]` |

M、K、N 必须为正，不接受其他 mode。版本 1 不支持稀疏 K 尾组：Sparse 要求 `K % 4 == 0`，不满足时拒绝，不能在核中偷偷改尺寸。M、N 不要求整除 tile；内部尾块仅计算有效元素。

首轮真实模型必测尺寸为 `M=197,K=192,N=576` 和 `M=197,K=576,N=192`，Dense/Sparse 都要测。格式本身不等于硬件支持任意尺寸；具体容量上限和尺寸白名单在新核配置中明确，超限调用在启动前拒绝。

## 3. AXI 拍、字节序与对齐

本约定使用 AXI4 Memory-Mapped `m_axi`，不是 AXI-Stream。所有数据缓冲区以 `ap_uint<128>` 为外部读写字，一拍 16 字节。

对每个独立缓冲区，约定低地址字节对应 128 bit 字的低位：

```text
第 q 拍的 byte lane j = bits[8*j+7 : 8*j]，j=0..15
内存字节地址 = buffer_base + 16*q + j
```

- INT8 每拍 16 个元素；INT32 每拍 4 个元素，按 little-endian 存储。
- 每个缓冲区以及合并 BO 中每层缓冲区的起始物理地址都要求 64 字节对齐；这是本项目约定，不是声称所有 AXI 访问必须 64 字节对齐。
- 逻辑数据只在整个缓冲区末尾补零到 16 字节，不改变行步长。多层共用 BO 时，层间可以留对齐空隙，空隙不属于层的数据。
- Host 分配并初始化完整尾拍；核只能读写各自已分配范围，不能依赖下一层缓冲区或额外 sentinel。
- 最后一个 Y 拍的无效 lane 写零；仅前 `M*N` 个 INT32 是输出。

定义 `align16(b)=16*ceil(b/16)`。地址、长度计算在 Host 使用至少 64 bit 整数，并先检查乘法和地址范围，避免整数回绕。

## 4. Sparse 的分组与排列

沿 K 分组，**每个输出列 n 都有自己的位置索引**：

```text
G = K / 4
T = G * N                         # 稀疏记录总数
t = g * N + n                     # g=0..G-1，n=0..N-1
```

每条记录保留两个槽位，顺序固定为位置从小到大：

```text
p0 = positions[g,n,0]
p1 = positions[g,n,1]
0 <= p0 < p1 <= 3

v0 = values[g,n,0]
v1 = values[g,n,1]

Wq[4*g+p0,n] = v0
Wq[4*g+p1,n] = v1
其余位置 = 0
```

因此，不能把某列的位置套用到所有 N 列。保留值允许为零，不能从 `values != 0` 反推位置或 mask。

### 4.1 W_data：两个 INT8 值

按 `g → n → 槽位 s` 排列，最内层变化最快：

```text
byte_offset(v0) = 2*t
byte_offset(v1) = 2*t+1

values_beat = t // 8
slot       = t % 8
v0_raw     = W_data[values_beat].bits[16*slot+7  : 16*slot]
v1_raw     = W_data[values_beat].bits[16*slot+15 : 16*slot+8]
```

`raw` 是 8 bit 原始位型，解码时按有符号 INT8 解释。**一个 128 bit values 拍装 8 条稀疏记录，每条两个值。**

### 4.2 W_meta：两个 2 bit 位置

每条记录用一个 4 bit 半字节，不使用完整 4 bit mask：

```text
code(t) = p0 | (p1 << 2)
bits[1:0] = p0
bits[3:2] = p1

meta_beat = t // 32
shift     = 4 * (t % 32)
code(t)   = (W_meta[meta_beat] >> shift) & 0xF
```

一个字节的低半字节存偶数 t，高半字节存下一个奇数 t。**一个 128 bit metadata 拍装 32 条记录的位置，配套 4 个 values 拍。**“配套”是索引关系，不要求总线按固定节奏交替传输。

| `(p0,p1)` | code（十六进制） |
|---|---:|
| `(0,1)` | `0x4` |
| `(0,2)` | `0x8` |
| `(0,3)` | `0xC` |
| `(1,2)` | `0x9` |
| `(1,3)` | `0xD` |
| `(2,3)` | `0xE` |

例如 `(1,3)` 的位置码是 `0xD`，而对应 mask 是 `0xA`；**二者不能混用**。

真实记录 `t<T` 只能使用上面六种 code；Host 打包器必须检查。末尾 `t>=T` 的 padding 填零，核必须忽略，不能把其 code=0 误报为真实记录错误。真实全零权重组仍使用合法的两个位置，例如 `(0,1)`，数值均为零。

### 4.3 为什么分成两段

不把每组的 20 bit 直接连续塞进一条流，避免单条记录跨越 128 bit 字边界；也不为方便对齐把每组扩成 32 bit，否则权重载荷将退回 Dense 的大小。

本版使用普通 DDR 数据缓冲区存 metadata，不借用 AXI 协议的 ID、USER 或其他侧带信号。`W_data` 与 `W_meta` 不需要相邻，地址分别传入。

## 5. 缓冲区长度与节省量

下表的分配长度含末尾整拍 padding，不含层间 64 字节对齐空隙：

| 缓冲区 | 有效字节数 | 分配字节数 |
|---|---:|---:|
| X | `M*K` | `align16(M*K)` |
| Dense W_data | `K*N` | `align16(K*N)` |
| Sparse W_data | `2*T` | `align16(2*T)` |
| Sparse W_meta | `ceil(T/2)` | `align16(ceil(T/2))` |
| Y | `4*M*N` | `align16(4*M*N)` |

Dense 模式下，Host 仍为 W_meta 提供至少一个 16 字节、起始地址 64 字节对齐的全零占位缓冲区；核必须完全不读取它，不以空指针作为默认调用约定。

每 32 条记录，原 Dense 权重为 `32*4=128 B`；Sparse values 为 `64 B`，metadata 为 `16 B`，合计 `80 B`。因此，**计入位置后有效权重载荷减少 37.5%，不是 50%**。

当前 c062 的每个 fc1/fc2 均有 `K*N=110592` 个权重：

| 范围 | Dense 权重 | Sparse values | Sparse metadata | Sparse 合计 |
|---|---:|---:|---:|---:|
| 单个选中层 | 110592 B | 55296 B | 13824 B | 69120 B |
| 12 个选中层 | 1327104 B | 663552 B | 165888 B | 829440 B |

这些尺寸无需尾拍补齐。以上只比较选中层的权重缓冲区，不含 X/Y、未剪枝层、scale/bias、其他模型参数、AXI 开销或文件头；**不能据此宣称整模型缩小 37.5% 或推理加速相同比例**。

## 6. 可手算的字节级例子

令 `M=1,K=4,N=2`，用于格式测试，不代表旧 IP 已支持该微型尺寸：

```text
X = [1, 2, 3, 4]

W[K,N] = [[ 0,  3],
          [-5,  0],
          [ 0, -2],
          [ 7,  0]]

t=0（g=0,n=0）：values=[-5,7]，positions=[1,3]，code=0xD
t=1（g=0,n=1）：values=[3,-2]，positions=[0,2]，code=0x8
```

内存低地址在左，其余字节补零至一拍：

```text
X：      01 02 03 04 00 00 00 00 00 00 00 00 00 00 00 00
W_data： FB 07 03 FE 00 00 00 00 00 00 00 00 00 00 00 00
W_meta： 8D 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
Y：      12 00 00 00 FD FF FF FF 00 00 00 00 00 00 00 00
```

计算结果：`Y[0,0]=2*(-5)+4*7=18`，`Y[0,1]=1*3+3*(-2)=-3`。

这组字节应成为 Python 打包器与 C++ 解码器共用的固定测试向量。

## 7. 接入 HLS / runtime 的边界

建议下一版保留三个 128 bit 主接口，绑定关系如下：

| 参数 | 建议 m_axi bundle | 方向 |
|---|---|---|
| X | gmem0 | 读 |
| W_data、W_meta | gmem1，共用同一 AXI Master | 读 |
| Y | gmem2 | 写 |

多个指针可以映射到同一 AXI 接口，但共用接口不意味着能够同周期无代价并读；本版不要求增加第四个 Master。实现时应分开组织连续加载循环，并检查综合后的位宽、burst 和实际资源。AMD 对同一接口的多个指针及通道机制的说明见 [UG1399：M_AXI Channels](https://docs.amd.com/r/2025.1-English/ug1399-vitis-hls/M_AXI-Channels)。

Host 写入的是 XRT BO 的设备地址，不是 CPU 虚拟指针；所有地址按 64 bit 处理。完成前不能释放或改写正在使用的缓冲区。

**新增 W_meta、mode 会改变控制 ABI。** 本文不臆造寄存器偏移，不复用旧 runtime 的硬编码地址表；后续以新 HLS 导出的驱动/寄存器定义为准，配套更新平台 metadata、xclbin 与 runtime 后才能板测。仅把总线保持为 128 bit，并不代表旧 IP 可直接替换。

启动前完成输入/权重/metadata 的必要 device sync，确认核和 AXI 访问完成后再做 Y 的 host sync；不能因加入 Sparse 而移除现有一致性和完成检查。

每层的软件打包清单至少记录：格式标识、mode、M/K/N、源候选与该层 NPZ 的 SHA256、各段有效/分配长度、各二进制段 SHA256。文件头不嵌入 DDR 数组，硬件地址直接指向有效载荷首字节。

## 8. 与当前 12 层候选的对应

只读来源：`../candidates/h576_sparse24_mlp12_c062_v1/weights/layer_XX.npz`。

- NPZ 中 `values` 已是 `int8[G,N,2]`；按 C-order 的原始值字节排列后补尾拍。不能把 NPZ 压缩文件本身当作 W_data。
- `positions` 目前每个位置占一个 UINT8；按第 4.2 节重新压成两个位置共 4 bit，而不是直接复制两个字节。
- `mask、Wq、W_fp32` 留在软件端校验，不重复传入 Sparse 核；`sw、bias` 留在软件后处理。
- 打包只转换表示形式，不重新剪枝、不重新量化、不改变任何保留值或位置。
- 层索引 `26,27,30,31,34,35,38,39,42,43,46,47` 的 mode 为 1；其他层 mode 为 0。原路由不变：qkv/fc1/fc2 在 PL，proj/head 在 PS；PS 层无需调用此核。

新打包产物另建目录，不覆盖候选 NPZ、ONNX、protocol.json 或哈希清单。旧 protocol.json 中 `NOT_FROZEN` 是该历史导出的真实状态，不直接改写为“已支持本协议”。

## 9. 实现前后的验收清单

以下为后续必须执行的测试要求，**不表示本文档创建时它们已全部通过**。

1. 打包→解包逐字节重建 Wq，并与原 NPZ 中 Wq 完全一致。
2. 六种位置组合、负数、零值保留槽、INT8 边界均正确；位置顺序、nibble 顺序及非法 code 检查正确。
3. 覆盖 `t=7/8` 的 values 换拍、`t=31/32` 的 metadata 换拍，以及每个缓冲区的短尾拍；验证尾部零 code 不被当成真实组。
4. 小矩阵字节向量与第 6 节完全一致；无逐行 padding、K/N 轴颠倒或重复传 mask。
5. 用本候选全部 12 层的公开 Xq/边界 Xq 核对：Sparse 结果等于使用**同一剪枝 Wq** 的 INT64 Dense 参考转 INT32；不是要求等于未剪枝权重的输出。
6. Dense 路径不读取 W_meta；无效 mode、非法 Sparse K、超容量尺寸、短缓冲区、地址未对齐在启动前被拒绝。
7. Python 通过后，再独立检查 C++ 解码、CSim、Cosim、综合端口和资源，最后才进行配套 runtime 板测。

对于由 Host 已检查的合法输入，核必须按约定得到唯一结果。metadata 损坏等运行期异常另行定义错误返回；未承诺出错时 Y 自动回滚，失败输出不得当作有效结果使用。

## 10. 依据与版本变更

本格式的分组和数值规则来自当前 c062 的 `protocol.json`；现有 128 bit 接口及旧 ABI 边界由公开 H576 包 README、`source/kernel.cpp` 核对。本文只读这些资料，没有修改原包。

创建本文时做过一次性、无文件输出的内存校验：第 6 节字节示例、六种位置码、30 组短尾拍/换拍尺寸、全部 12 层 NPZ 的编码与重建通过；以重建 Wq 计算的 935424 个 INT32 输出与既有公开/边界算术样本一致。原候选全部文件的哈希检查通过。此结果仅核对格式，不等于已交付或独立验收 Python 打包脚本，更不等于 HLS、Cosim 或板测通过。

`values/positions` 的具体编码、排列和对齐是**本项目选择**，不是声称 NVIDIA 或 AXI 协议规定了同样的模型压缩格式。AXI 主接口与 burst 的工具行为参考 [AMD UG1399：AXI4 Master Interface](https://docs.amd.com/r/2025.2-English/ug1399-vitis-hls/AXI4-Master-Interface)。

后续改变总线宽度、位置编码、索引顺序、行步长或 padding 规则时，必须升级格式标识，并同步打包器、testbench、HLS 和 runtime；不能让同名格式对应两套解释。

本地研发文档先保存在 `h576_sparse24/docs/`；合入团队仓库时由 `docs/interface.md` 引用相应版本，不再另写一套互相矛盾的格式说明。
